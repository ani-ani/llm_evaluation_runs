Design a sequential Verilog module named 'tarot_knight_solver' that computes the minimum cost to reach (0, 0) from a start position, based on a simplified Tarot Knight problem.

Problem Adaptation:
- Max 4 tarot cards (N=4).
- Coordinates (r, c) are 8-bit signed integers (range -128 to 127).
- Card values (a, b) and price (p) are 8-bit unsigned integers.
- Knight starts at Card 0's position.
- Knight must land on a card's position to buy it (instant cost addition).
- Knight retains moves from all purchased cards.
- Goal: Reach (0, 0) with minimum total cost.

Inputs:
input clk // Clock signal
input rst_n // Active-low reset
input start // Start computation
input [7:0] card_r [0:3] // Card row positions (signed)
input [7:0] card_c [0:3] // Card column positions (signed)
input [7:0] card_a [0:3] // Card value a
input [7:0] card_b [0:3] // Card value b
input [7:0] card_p [0:3] // Card price

Outputs:
output reg [15:0] min_cost // Minimum cost found (0xFFFF if impossible)
output reg done // High when computation complete

Implementation Details:
The module should use a state machine (IDLE, CHECK_REACHABILITY, UPDATE_COSTS, FINISH).
1. IDLE: Wait for start.
2. CHECK_REACHABILITY: Determine which cards are reachable using the currently owned set of moves. A card is reachable if its position can be reached from any currently owned card's position using the moves from any owned card. Since moves are symmetric (e.g., (a,b) implies (b,a), (-a,b), etc.), checking reachability reduces to checking if the displacement vector (dr, dc) between two cards satisfies the GCD property of the move vectors, or simply checking if the displacement can be formed by the union of moves. However, for this simplified hardware version, we will use a state machine that iterates through permutations of card purchase orders (up to 4! = 24 permutations). 

3. UPDATE_COSTS: For each valid permutation (order of visiting cards), calculate the cost. A permutation is valid if:
   - Start: Knight at card 0's position.
   - Step 1: Move from card 0 to card i (if reachable using card 0's moves). Pay card i's price.
   - Step 2: Move from card i to card j (if reachable using card 0 + card i's moves). Pay card j's price.
   - ... and so on.
   - Finally, check if (0,0) is reachable from the last visited card using the accumulated moves.
   
   Reachability Logic (Simplified for Hardware):
   A displacement (dr, dc) is reachable by a set of moves if the vector (dr, dc) lies in the linear integer span of the move vectors. Since we only care about existence for small numbers, we can check if 'dr' and 'dc' can be reduced to 0 using the Euclidean algorithm logic based on the available a/b values (specifically, checking if GCD of all available moves' linear combinations divides the displacement). However, a simpler hardware check for this benchmark is: 
   - Can we reach a card at (r_t, c_t) from (r_s, c_s) if we have moves (A, B)? 
   - Check if there exists integers x, y such that x*A + y*B = dr and x*B + y*A = dc is complex. 
   - Simplification: Use a bitmask reachability approach. If we own moves, we can reach any point in the connected component of the infinite grid defined by those moves. 
   - For this specific module, we will use a pre-computed reachability check based on the GCD of coordinates. A displacement (dr, dc) is reachable if GCD(dr, dc) is divisible by the GCD of the move set (converted to 1D). 
   - Actually, to keep it implementable: The module will verify reachability by checking if the displacement (dr, dc) satisfies the condition that it can be expressed as linear combinations of the move vectors. We will assume a simplified check: if the target is within a small bounding box, we can just brute-force BFS, but here we use the math property: reachable if the target position is in the lattice generated by the moves. Since we only have 4 cards, we can unroll the logic.

4. FINISH: Output min_cost. If no valid path found, output 0xFFFF.

Latency: Approx 100-200 clock cycles.

Constraint: The module assumes the input coordinates and values fit within 8 bits. The GCD calculation for reachability should be done iteratively (Euclidean algorithm state machine).

Note: The module must handle signed coordinates for displacement calculation (r_target - r_source). Use 2's complement arithmetic.

The module structure:
- Registers to store current permutation state.
- Registers to store accumulated moves (a_values, b_values).
- A combinational block to calculate GCD of a set of numbers (for reachability check).
- A combinational block to calculate displacement and check if displacement is divisible by the GCD of moves.
- State machine to iterate through permutations (0,1,2,3), (0,1,3,2), etc. (Total 24 states or sequential logic to generate them).

Since 24 permutations is large for a naive FSM, we will use a sequential counter for the permutation generation (0 to 23) and a secondary FSM for checking the specific permutation's validity and cost.

Reachability Check Logic:
Displacement (dr, dc) is reachable if:
1. dr == 0 && dc == 0.
2. Or, if we have moves, check if (dr, dc) is in the lattice generated by the moves. 
   Simplification: If we have moves with values (a1, b1), (a2, b2)... we calculate the GCD of all 2*a, 2*b, a+b, a-b (or similar). But simpler: 
   We will calculate the GCD of all 'a' and 'b' values of owned cards. Let G be that GCD. 
   Then check if (dr, dc) is reachable. For knight moves (a,b), the lattice condition is that dr and dc must be divisible by GCD(a,b). 
   Actually, for moves like (a,b) and (b,a), the lattice is denser. 
   We will check if `dr` and `dc` have the same parity if GCD(a,b) is even? 
   Let's stick to a robust check: A point (r,c) is reachable from (0,0) with moves (x,y) if (r,c) is in the lattice generated. 
   We will use a specific logic: 
   Calculate G = GCD of all owned 'a' and 'b' values. 
   Check if `dr` is divisible by G and `dc` is divisible by G. 
   *Correction*: This is not sufficient for (a,b) moves. 
   *Hardware simplification*: We will assume a generic reachability checker that calculates the GCD of all displacements that can be formed. 
   Actually, for the purpose of this benchmark, we will implement a specific check: 
   A displacement (dr, dc) is reachable if `dr % gcd_all == 0` AND `dc % gcd_all == 0`, where `gcd_all` is the GCD of all `a` and `b` of owned cards. This is a simplification but works for many cases and is implementable.

Stop Condition: The module stops when it has evaluated all 24 permutations of the 4 cards. Note that cards are indexed 0..3. Card 0 is start. 
If N < 4 in the problem context, the input will pad with dummy cards or we assume N=4 for the hardware interface but logic ignores unreachable cards.

Actually, to make it robust: The inputs are 4 cards. If the user wants N<4, they repeat the last card or set it to unreachable. 

Refined State Machine:
- IDLE
- PERMUTE: Generate next permutation of {1,2,3}.
- TRACE_PATH: 
  - Start at card 0 (pos r0, c0). owned_a = {a0}, owned_b = {b0}.
  - Iterate through the 3 cards in the current order.
  - For each card i: 
    - Calculate dr = card_r[i] - current_r, dc = card_c[i] - current_c.
    - Check reachability using owned_a/b.
    - If reachable, add cost, update current_r/c, add card i's a/b to owned.
    - If not reachable, this permutation fails.
  - After visiting all 3 cards (or stopping if fail), calculate dr = 0 - current_r, dc = 0 - current_c.
  - Check reachability to (0,0).
  - If reachable, update min_cost.
- FINISH: Set done high.

Latency: ~200 cycles.
Module Name: tarot_knight_solver

Note on GCD logic for reachability: 
We need to check if (dr, dc) is reachable with moves A, B. 
The lattice generated by vectors (A,B) and (B,A) and signs covers all points (x,y) where x,y are multiples of GCD(A,B) under certain conditions, but strictly speaking we need a robust check. 
For this hardware spec, we will implement a generic GCD check. The reachability function will compute the GCD of all owned moves' `a` and `b` values. Let `g = gcd(a0, b0, a1, b1...)`.
Then it checks if `dr % g == 0` and `dc % g == 0`.
This is a simplification but allows a deterministic hardware implementation.

The GCD calculation unit will be a sequential state machine (Euclidean algorithm) shared across all checks.
